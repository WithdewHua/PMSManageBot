# 转盘接口变更与管理员操作

本文面向维护者和管理员，不是普通用户活动规则或限额提示文案。

## 用户接口的破坏性变更

配置与开奖结果不再向用户返回 `probability`。字段直接删除，不返回 `null`、固定假值或编码值。服务端内部仍保留完整权重，用于原有选奖逻辑；本次不改变基础奖池或小概率保护算法。

### 获取公开配置

`GET /api/luckywheel/config` 只返回：

```json
{
  "items": [{"name": "积分 +10"}, {"name": "邀请码 1 枚"}],
  "cost_credits": 10,
  "min_credits_required": 30
}
```

无论调用者是否为管理员，该接口都保持公开结构。`gen_privileged_code`、随机性调整参数、全服或个人配额及使用量均不返回；不能通过 `admin=true` 等查询参数获取完整配置。

### 单抽和十连抽

`POST /api/luckywheel/spin` 和 `POST /api/luckywheel/spin-ten` 继续要求有效 Telegram 认证。

单抽结果示例：

```json
{
  "item": {"name": "积分 +10"},
  "credits_change": 10.0,
  "current_credits": 100.0,
  "used_free_spin": false,
  "free_spin_source": null
}
```

十连抽保留 `results`、`total_credits_change` 和 `current_credits`。每个 `results[]` 项使用上述单次结果结构。名称是最终实际结算的奖项；没有候选奖项、重选原因、概率或配额元数据。

旧客户端必须移除对 `item.probability` 或 `items[].probability` 的依赖。普通转盘按奖项名称和索引绘制、定位及播放动画，不应在前端自己抽奖。原有免费次数展示、积分刷新和十连结果列表保持不变，不新增限量说明、触顶提示或库存展示。

## 管理员接口

以下管理接口必须同时通过 Telegram 认证和管理员权限校验。普通用户收到 403，未认证请求被拒绝。页面隐藏管理入口不是权限措施。

| 方法与路径 | 功能 |
| --- | --- |
| `GET /api/luckywheel/admin/config` | 完整奖池配置，包括 `probability` 和特权发码开关 |
| `PUT /api/luckywheel/config` | 原有完整奖池保存入口，继续仅管理员可用 |
| `GET /api/luckywheel/admin/invite-quotas` | 读取全服及个人自然周限额 |
| `PUT /api/luckywheel/admin/invite-quotas` | 保存限额，不清零实际已用量 |
| `GET /api/luckywheel/admin/invite-quota-stats` | 当前周发放和重选核对信息 |

统计接口可通过 `week_start_ms` 指定周期，传服务端使用的自然周起点毫秒时间戳。不得把滚动七天或浏览器本地时区起点误当作该值。

管理员面板必须改用新的完整配置读取接口，不能继续从公开 `/config` 加载权重后保存。普通转盘和管理员内嵌的普通转盘预览仍使用公开读取函数。

### 限额配置

保存时提交两个非负整数字段：

```json
{
  "global_weekly_limit": 30,
  "personal_weekly_limit": 5
}
```

- 周期为北京时间（UTC+08:00）周一 00:00 至下周一 00:00，前闭后开。
- 0 表示禁止对应范围发放邀请码，不是无限制。负数、小数、布尔值、字符串或缺失字段无效。
- 付费、免费和十连抽，以及普通码与特权码，共用限额。
- 已使用或兑换积分的邀请码仍计入发行量；用户换绑不重置个人使用量。
- 调低至已用量以下不会撤回已有码，后续不再发码；调高只增加剩余空间。
- 已提交配置对之后开始的新结算生效；进行中的结算保持自己的配置快照。
- 触顶后服务端排除全部邀请码奖项，在本次抽奖内按其他奖项权重重选，只扣费或消耗免费机会一次。重选仍可能得到原有负向积分奖项。
- 奖池必须有至少一个正权重的非邀请码奖项；只有邀请码的奖池不能作为有效后备池使用。

### 核对统计

统计响应提供：

- `initialized`：是否具备有效初始化依据；不能将未初始化当作正常零用量。
- `week_start_ms`、`week_end_ms`：自然周边界。
- `global_used`、`global_limit`、`personal_limit`：实际发行量与管理限额。
- `historical_issued`、`new_issued`：历史回填量与上线后新增量，两者之和应等于实际发行量。
- `global_blocked_count`、`personal_blocked_count`、`both_blocked_count`：限额命中计数；全服/个人标志可以同时为真，汇总时不要把三个值直接相加当作独立抽奖次数。
- `first_exhausted_at_ms`：可从证据确定的首次耗尽时间，未知时为 `null`。
- `users`：`[{"username": ..., "issued": ...}]`，按 Telegram username 核对；本地缓存没有 username 时为 `null`，前端显示“未设置用户名”，不返回 Telegram ID。
- `sources`：`[{"source": ..., "issued": ...}]`，历史无法确定的来源保持 `null`，不要根据参与费用推断。

管理读取失败应明确显示错误，不能把连接失败解释成零用量或保存成功。管理员也不能根据当前未使用邀请码库存推算剩余额度。

## 发布与回滚注意事项

1. 协调后端与管理员前端发布：新的公开响应会使依赖旧读取路径的管理员面板失去权重。
2. 数据库结构迁移和首周历史初始化是独立步骤。首次上线必须计入本周已经发出的转盘邀请码，历史超限保留真实数量，不截断成 30/5。
3. 在受控维护窗口核对历史、完成初始化并验证管理员核对信息后，再开放抽奖。历史无法可靠确认时停止启用，不能从零释放一份新额度。
4. 不允许旧版无限额写入者与新版服务混跑。回滚时先关闭抽奖，保留配额和审计依据；旧服务不再提供本次新增的限额保证。
5. 服务端不直接返回内部参数，不代表用户无法根据自己的开奖结果推断频率；不要将这两个概念混同。

## 回归检查清单

自动化 HTTP 契约与权限检查位于 `tests/test_luckywheel_public_api.py`。前端发布前还应在隔离环境检查：

- 普通转盘配置和单抽/十连原始响应均无 `probability`、内部配额和候选元数据。
- 免费次数展示、单抽动画、十连列表和积分刷新正常。
- 管理员完整配置可读取并保存，普通用户不能访问管理接口。
- 管理员内嵌普通预览仍能正常运行。
- 管理限额 0 的显示含义正确；保存或加载失败有明确提示，不清空有效历史快照造成误解。
- 限额重选不会先展示邀请码中奖，也不新增任何面向普通用户的触顶说明。
