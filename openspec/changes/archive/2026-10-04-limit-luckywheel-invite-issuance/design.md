# Design

## Context

动机与范围见 `proposal.md`；行为契约见两份 delta spec。

现有 `luckywheel.service` 在事务外调用纯选奖函数，`repository.spin_tx` 在同步事务内消耗免费机会或积分、发放奖励并写 `WheelStats`；十连抽预选十个候选，在一个事务内逐项结算。邀请码通过 invitation 的 `issue_codes_tx` 发出，通知发生在提交后。新增限制应进入这条公共结算路径，不能只包装 HTTP 单抽入口。

`WheelStats` 保存奖项名称、TG ID、秒级 Unix 时间戳和可空的来源，没有实际发码数量或邀请码关联。当前发奖规则遇到邀请码效果发一枚，现有统计却只按名称精确匹配“邀请码 1 枚”，不能直接复用其累计或滚动七天指标作为新自然周计数。

用户和管理员目前共享 `GET /luckywheel/config`，完整奖项和开奖结果均包含 `probability`。`WheelAdminPanel.vue` 还内嵌普通 `LuckyWheel.vue` 作为预览，因此不能把共享用户读取函数直接改成管理员接口。

本变更涉及新持久化状态、并发控制、首周数据迁移和响应兼容性，必须提供设计文档。

## Goals / Non-Goals

**Goals:**
- 用数据库事务保证多进程下两层上限，保持一次抽奖一次结算及十连抽整批回滚。
- 历史初始化、运行期发行和限额重选可核对，用户换绑后使用量不丢失。
- 用户响应采用明确的公开结构，与管理员完整配置解耦。

**Non-Goals:**
- 不更改基础概率、随机性保护、其他奖项效果和邀请码权益。
- 不做滚动七天、每日分批释放、全渠道邀请码库存或新的请求幂等协议。
- 不增加用户限额提示；不扩展为通用抽奖平台或大型运营分析系统。

## Decisions

### 1. 周期与运行时配置

沿用 `settings.TZ` 的固定 UTC+08:00，以周一 00:00 为起点，存储 Unix 毫秒周期键，历史 `WheelStats.timestamp` 查询边界转换为秒；所有范围使用 `[start, end)`。时间只由服务端提供，纯规则函数接收时间及时区参数。结算事务入口捕获一次时间与配置快照，十连抽共用，不在批内或等待锁后重新取得新周额度。

在 luckywheel 域新增独立的 `DomainConfig` 文档，例如 `luckywheel.invite_quotas`，存储于 `lucky_wheel / invite_quotas`：`global_weekly_limit=30`、`personal_weekly_limit=5`。不将其嵌入原用户可读奖池文档，不加入 `.env`。配置只允许数据库可存储范围内的非负整数（0～2147483647），0 表示禁止该范围发码；个人值大于全服值不构成错误，全服约束仍有效。拒绝超范围值，避免审计限额快照写入时发生整型溢出。

首次默认值由所属仓储在尚无账本记录时受控创建；`business_config.CONFIGS` 保留该声明用于统一管理，但 `seed_all()` 排除其自动播种。已有账本后配置丢失时，管理员读取、重复初始化和重启都不得补回默认值而恢复发码；当前结算必须继续失败，直至维护者明确恢复有效配置。

已提交配置对随后开始的新结算生效，进行中的结算使用原快照；改值不修改已用量。降低上限至已用量以下不撤回历史发放，后续邀请码候选重选。配额快照使用仓储内的权威存储读取与校验，不能依赖可能跨进程滞后的缓存来判定硬上限。采用现有 `DomainConfig` 声明及管理员更新机制，但在发奖事务中通过 core KV 机制读取对应原始文档并严格校验；存储损坏或查询失败不得默认为 30/5 继续发码。

**替代方案：**定时清零计数容易在停机、重复任务或多实例中出错；按周期键新增状态无须重置任务。把运行计数写入配置文档会混淆配置与业务状态，故不采用。

### 2. 全服周记录与按事件汇总的个人使用量

新增 luckywheel 域自有的两类持久化记录，名称可按现有命名规范落地：

- **全服周记录**：以 `week_start_ms` 为唯一键，包含已发总量、初始化模式（首周历史 / 后续空周）、初始化完成时间和首周回填核对摘要。用于序列化同周邀请码候选及核对发行总数。
- **邀请码决策审计**：关联唯一的 `WheelStats.id`，保存周期、`tg_id`、实际发码数量（当前规则为 0 或 1）、来源、候选与最终奖项、全服及个人触顶标志、适用上限快照、时间、历史回填标记。实际发码可记录特权状态，历史无法确认时为空；不复制邀请码明文。

仅对邀请码候选或历史邀请码发放建立审计，普通非邀请码结果继续只写现有统计，避免放大所有抽奖的存储量。以 `(week_start_ms, tg_id)` 建索引，个人使用量由审计实际发码数量求和；被淘汰的候选数量为 0。全服已用量必须等于本周全部审计实际发码数量之和。

不另建 `(week, tg_id)` 唯一个人计数器。发码本就受全服周行串行化约束，每周正常成功发码初始上限仅 30，带索引汇总成本可控；同时避免换绑时两个用户计数行碰撞。审计 TG ID 声明 `info={"tg_id": "user"}`，注册到 luckywheel 的换绑列清单；成功换绑直接迁移审计记录的归属，个人使用量自然合并，全服计数不变。其他领域的换绑拒绝规则保持不变，不为配额另开绕过入口。

新增自增主键采用 SQLite 兼容的整数类型；历史 `WheelStats` 主键值及 PostgreSQL BIGINT 类型保持不动。实施验证发现旧 SQLite BIGINT 主键不能原生自增，因此模型增加 SQLite INTEGER 变体，结构迁移用 batch alter 保留既有 ID 并修正 SQLite 物理类型；已加入外键开、关两种模式的迁移往返测试。不得把新状态加入 Statistics 等身份宽表。

### 3. 在公共仓储事务中完成最终裁决

服务层可继续预选候选，同时准备非邀请码后备池并验证其至少存在一个正权重奖项；仓储接收候选、有效后备池与随机性快照。后备池排除所有按现行效果判定会发邀请码的奖项，而不是只排除某个固定名称。

所有路径在 `spin_tx` 等公共结算内执行相同逻辑，包括兼容单抽调用和十连抽。当前候选不是邀请码时，直接执行原奖品效果。邀请码候选必须通过周额度裁决后，才消费特权码开关、调用 invitation 发码或设置提交后通知标志。

```text
candidate --> non-invite --------------------------+
     |                                             |
     v                                             |
lock week, read both usage values                   |
     |                                             |
     +--> both available --> issue invite ----------+
     |                                             |
     +--> either exhausted --> pick non-invite -----+
                                                   |
                                                   v
                                   settle + stats + audit
                                                   |
                                                   v
                                                commit
```

重选只调用纯选奖逻辑，最多进行一次对已过滤奖池的选奖，不再次调用完整 `spin`。纯规则使用现有随机性调整配置，不读取数据库或业务配置。最终 `WheelStats` 与用户返回值只描述实际奖项；后台审计保留原候选与触顶原因。

后备池无效时，管理保存拒绝；运行期仍进行防御校验，使旧无效配置在扣费、免费次数消耗前失败。故障返回现有中文领域错误风格，不返回完整配置或配额值。

### 4. 锁顺序、SQLite 与失败语义

保持现有免费机会认领与用户积分行的事务顺序；在已锁定当前用户积分行后，邀请码候选取得本周期全服周行的数据库写锁，再读取个人审计汇总、检查两层配额并写入最终结果。单抽和十连抽必须使用同一顺序，十连抽不能在外层与内层反向获取锁。

首个访问新周的请求通过唯一约束与事务安全的 insert-if-absent 创建周记录。不能只依赖 SQLite 无效的 `SELECT FOR UPDATE`：使用对周行的实际条件写入或显式写锁策略，确保读取个人使用量前已经进入受数据库保护的写事务；PostgreSQL 对同一周行实施行级锁。计数增量同时带上限条件并检查受影响行数，作为防御校验。初始化竞争的唯一键冲突通过安全 upsert 或 savepoint 处理，不污染外层事务。

在周行保护下先检查全服和个人使用量；任一触顶时两者都不增加。允许发码时，全服计数增加、发码、最终统计和审计在同一个外层事务提交。不存在“先扣全服额度、个人失败后忘记归还”的半成功状态。数据库锁冲突或读写失败不是业务触顶：应回滚整个结算，不以重选掩盖错误。SQLite 忙锁可以返回安全的失败，但不得超发或部分扣费。

个人审计迁移与现有换绑流程共用身份行锁；实现时核对双方锁顺序，避免为换绑新增与发码相反的全服锁依赖。十连抽第三次等后续操作失败时，前面已占额度、发码及审计全部回滚。所有外部通知仍在提交后执行。

### 5. 首周历史回填是受控上线步骤

用户已确认：上线前本周已发的邀请码计入配额，历史超限不撤销，只阻止继续发行。

新建一个只做编排的运维脚本，例如 `scripts/initialize_luckywheel_invite_quotas.py`，默认 dry-run。业务查询与写入仍在 luckywheel 仓储，通过服务能力调用，不把 SQL 放在脚本中。脚本按北京时间当前自然周查询 `WheelStats`，统计全部来源（包括 NULL），不能仅匹配字面“邀请码 1 枚”，也不能根据费用推断免费来源。

先按历史奖项名称分组，用现有纯效果判定识别候选发码记录，报告 TG ID、原统计行 ID、名称、来源、时间和合计。历史统计不包含真实邀请码关联，自动分类只能提供候选基线，不能证明记录完整性。维护者必须核对自定义奖项语义、历史记录完整性及本周部署历史；不确定或发现缺失时停止启用，不能自动按零、截断到上限或猜测数量。

确认后在所有旧版抽奖写入者和相关调度器停止的窗口执行 apply：校验报告与当前源记录摘要一致，为每条确认的历史发码统计生成一条标记为历史的审计，汇总全服周计数，原子写入完成标记。回填不生成邀请码、不改余额、不发通知。实际历史数量允许大于新上限。

首周周记录的历史初始化完成状态是启用依据。重复 apply 校验既有基线后无操作，不重放、不覆盖上线后新增计数；源数据不一致则明确报错。未发现成功初始化基线时，运行期不得自行创建“首周零用量”：相关抽奖拒绝结算并回滚，部署保持维护状态。只有首周基线已完成之后，更晚的新自然周才允许懒创建空周记录。若维护窗口跨周，必须以重新确认的当前周报告初始化，不能把旧周报告当成当前周基线。

**替代方案：**上线时清零已被用户否决；启动时自动扫描并猜测历史含义无法提供可靠限额保证。历史数据回填属于受控数据操作，不塞入 Alembic 结构迁移。

### 6. 用户 DTO 与管理员入口分离

保留内部 `LuckyWheelItem` 和完整奖池模型，新增只含 `name` 的公开奖项 DTO，以及明确白名单字段的公开配置与开奖结果 DTO。配置公开字段限定为 `items`、`cost_credits`、`min_credits_required`，开奖保留现有业务字段但奖项不带 `probability`。内部提交结果可保留审计元数据，但不得使用通用 dump 将其透传给用户。

接口方案（均指 `/api` 挂载下的相对路由）：

| 路由 | 用途与权限 |
| --- | --- |
| `GET /luckywheel/config` | 保留用户读取，响应改为公开 DTO |
| `POST /luckywheel/spin`、`POST /luckywheel/spin-ten` | 保留原认证和业务字段，所有结果奖项使用公开 DTO |
| `GET /luckywheel/admin/config` | 新增管理员完整奖池读取，认证加管理员权限检查 |
| `PUT /luckywheel/config` | 保留既有管理员保存路由，增加有效后备池校验 |
| `GET/PUT /luckywheel/admin/invite-quotas` | 管理员读取和更新独立配额文档 |
| `GET /luckywheel/admin/invite-quota-stats` | 管理员按周查看配额与审计汇总 |

现有 randomness、全服统计等管理接口继续保持权限校验，用户状态及历史活动统计不新增配额状态。黑盒不阻止从既有开奖结果推断频率，也不要求删除用户既有活动历史。

`wheelService.js` 保留 `getLuckyWheelConfig` 的公开语义，新增命名明确的管理员读取与配额操作函数。`WheelAdminPanel.vue` 改用管理员完整读取，添加限额配置及必要的当周核对信息；限额值仅从管理员接口加载，前端静态包不硬编码 30/5 初始值，读取失败不得显示伪造的零用量或默认上限。其嵌入的普通转盘预览仍走公开接口。普通 `LuckyWheel.vue` 不新增限额 UI，奖项位置继续由名称和索引确定。

不通过返回 `null`、假概率或编码值维持旧字段兼容；这是明确的响应破坏性变更，应协调管理员前端发布。管理员 OpenAPI 中存在概率字段定义不等同于向用户返回实际权重，真正需要隔离的是运行时参数与数据访问。

### 7. 后台审计范围与代码组织

管理汇总提供当前适用上限、实际使用量、首周历史量、上线后新增量、全服/个人/同时触顶次数、按用户及来源分布，以及可证实的首次耗尽时间。两种触顶用独立标志表示，避免同时触顶被错误归为单一原因。历史 NULL 来源保留未知，不推断为付费；历史特权状态、耗尽时间没有可靠证据时返回未知，不伪造。聚合只读取 luckywheel 自有表，不新增跨域业务 SQL。

现有 `repository.py` 已接近千行，新增仓储能力时按项目规则转成同名 `repository/` 包，保留现有模块级公共接口与兼容符号，按抽奖、统计、免费次数、配额子主题组织。不得另建绕过架构检查的顶层 SQL 模块。此拆分是本次仓储扩展的实现细节，不增加独立业务能力。

## Risks / Trade-offs

- [全服额度可能在周初耗尽，少数用户可能占满] → 接受 30/5 的预算策略；用管理员统计观察，不自动提高额度或暗改概率。
- [自然周边界可在短时间内释放两周额度] → 这是已选自然周语义，单个结算固定周期，不在本次改成滚动窗口。
- [全服周行有竞争] → 仅邀请码候选进入该临界区；真实低概率下通常低频，用可丢弃 PostgreSQL 验证并发，不牺牲原子性。
- [审计会记录被淘汰候选，数量不受 30 枚上限限制] → 建立周期和用户索引，仅记录邀请码候选；不在本次引入自动删历史任务。
- [用户看不到限制，仍可能观察到频率变化] → 按已确认产品要求不新增说明，但不把“不返回参数”表述为无法统计推断；管理员保留解释与排障依据。
- [旧前端管理员读取失去权重] → 新管理读取与前端一起发布，普通前端的名称式开奖应继续兼容。
- [历史记录不完整会低估首周用量] → 维护窗口 dry-run、人工核对与摘要校验；不可靠则停止上线，不能静默空基线启动。
- [回滚旧服务会绕过限额] → 回滚期间关闭抽奖流量，保留新表和审计，不将旧版服务当作仍具有限额保证。

## Migration Plan

1. 在本地完成模型、仓储、接口及客户端实现和回归；新模型接入注册与 TG 换绑清单。编写 Alembic 结构迁移，不在其中做首周业务回填。
2. 在隔离的可丢弃 PostgreSQL 上，以包含旧统计数据的 pre-head 基线执行 upgrade → downgrade → upgrade；验证 SQLite 兼容性。生产复制数据演练使用隔离容器、假凭据与空通知，不触碰原数据库。
3. 进入维护窗口，停止所有旧版抽奖写入入口和相关进程；备份数据库。通过一次性容器显式执行 `alembic upgrade head`，不依赖启动脚本吞掉迁移错误后的继续启动。
4. 对当前自然周执行初始化 dry-run，维护者核实历史后 apply，核对全服与个人总数、摘要和完成标记。失败则保持关闭，不启动可发码服务。
5. 部署新版后端及管理员前端，确认用户接口已无内部参数、管理员接口受保护、初始化量正确，再开放抽奖。后续自然周自动使用新周期键，不安排清零任务。
6. 观察 2～4 个完整周的发行量与触顶分布；上限调整只通过管理员运行时配置，不修改历史用量。
7. 若需回滚，先关闭抽奖并停止相关写入，再回退应用与前端；优先保留新表、审计和初始化依据。若确需降级结构，先导出这些记录；再次启用新版必须重新核对本周所有历史，不能沿用过期基线。不得在旧新版混跑时声称配额仍受保证。

## Verification Strategy

- 纯规则：周一边界、UTC 到北京时间转换、秒/毫秒边界、所有邀请码名称的效果分类、后备池过滤与权重保护保持不变。
- 事务：30/5 两层上限、0 上限、免费与付费共享、普通/特权共享、十连批内耗尽、失败回滚、存储故障不降级发奖、候选被淘汰不消费特权开关。
- 并发：独立连接争夺最后额度、同用户并发、新周建行竞争、单抽与十连交错；验证真实 PostgreSQL 行锁以及 SQLite 不靠 FOR UPDATE 的安全性。
- 数据：首周已用与超限、NULL 来源、自定义名称、报告变更检测、重复初始化、未初始化拒绝、跨周重做报告、审计与计数一致。
