## Why

礼包的领取资格目前只有三个固定字段（最低积分、要求 Premium、要求绑定），而且资格不满足的用户完全收不到提醒。常见的运营需求因此都做不了：
- 给一批指定用户发补偿（如受故障影响的用户）；
- 做「活动期间玩满 N 局」的任务型福利；
- 用「或」组合跨游戏的条件（如「转盘 50 次或 21 点 100 手」）；
- 提醒还差一点就能领的用户去完成任务。

## What Changes

- **资格拆成两份条件列表**（**BREAKING**：管理端 API 以 `audience` / `requirements` 取代 `eligibility`）：
  - **受众**（`audience`）：礼包给谁。不满足的用户完全看不到这个礼包。
  - **领取条件**（`requirements`）：要做到什么。不满足的用户能看到礼包、看到进度，并会收到任务提醒。
  - 两份列表用同一套类型化条件，放哪一份由管理员决定。「指定名单」只能用在受众里。
- **条件词汇**：
  - 状态型：指定名单（包含/排除）、Premium（有/无）、绑定、积分区间、持有勋章、已领取某礼包。
  - 计数型：大转盘局数、21 点手数（可加最低注额、准确率）、夺宝期数、大预言家下注数、竞拍场数、锦标赛参赛数、邀请人数、累计观看时长。
- **计数的三种时间范围**：历史累计 / 礼包开始后 / 最近 N 天，由每个计数条件自选。邀请人数与观看时长只支持历史累计（没有逐条时间记录）。
- **「或」组合**：条件列表最外层是「并且」，其中任一项可以是「满足其一即可」的一组。组内不再嵌套。
- **任务进度展示**：用结构化的逐项进度（如「活动期间付费转盘 12/50」）取代原先的一段原因文字。礼包状态 `ineligible` 拆为「不可见」与 `in_progress`（**BREAKING**：用户端 API 的 `ineligible_reasons` 由 `requirements` 进度取代）。
- **任务提醒**：开屏提醒增加「待完成」一类，与「可以领了」分开计次、分开按天节流，同一个汇总弹窗内分两块展示。任务提醒次数上限按礼包配置，设为 0 即不发。
- **受众锁定**：用户第一次被判定属于某礼包的受众时记录下来，此后不因受众条件变化而失去这个礼包。指定名单例外，名单增删实时生效。
- **任务截止与领取截止分开**：可选的任务截止时间。截止后计数冻结，进入「仅可领取」阶段，直到礼包结束。
- **名单型礼包开始时私信通知**：受众含指定名单的礼包，可选在开始时给名单内的每个用户发一条 Telegram 私信。
- **名单录入辅助**：管理员可粘贴混合的 tg_id / Plex / Emby 用户名，保存前统一解析为 tg_id，解析不了的逐条列出。
- **开始后的编辑限制**：礼包开始后，开始时间、奖励、领取条件的结构、非名单的受众条件都不可改。只允许放宽：延长任务截止与结束时间、增加份数、降低计数目标、增删名单成员。
- **兼容旧礼包**：已有礼包的 `eligibility` 在读取时转为等价的领取条件，其任务提醒上限视为 0，行为与改动前一致。

## Capabilities

### New Capabilities

（无）

### Modified Capabilities

- `gift-pack`: 下列需求都有变化：
  - 礼包定义：新增受众、领取条件、任务截止、任务提醒上限、开始通知开关；
  - 领取资格：改为类型化的领取条件，带时间范围、「或」组合与进度；
  - 生命周期：新增「仅可领取」阶段；
  - 礼包中心列表：不可见与进度展示；
  - 开屏提醒：新增任务提醒，与领取提醒分开计次与节流；
  - 领取：受众锁定与冻结的计数参与复核；
  - 管理端：名单解析、开始后的编辑限制、新统计项。

  另新增：受众、受众锁定、计数条件与时间范围、条件组合、名单型礼包的开始通知。

## Impact

**后端**

- `src/app/models/models.py`：
  - `GiftPack` 新增 `audience`、`requirements`、`task_end_at`、`max_task_prompt_count`、`notify_audience_on_start`；
  - `GiftPackUserState` 新增 `audience_locked_at`、`task_prompt_count`、`last_task_prompted_at`、`start_dm_sent_at`。
- `alembic/versions/`：新增一个迁移（只加列，全部可空或带服务端默认值）。
- `src/app/webapp/schemas/gift_pack.py`：条件判别联合、`any_of` 组、进度视图模型；创建与编辑请求去掉 `eligibility`。
- `src/app/databases/db.py`：
  - 条件求值器与各计数器（复用调用方的 session）；
  - 旧 `eligibility` 的读取适配；
  - 受众判定与锁定；
  - 列表、开屏提醒、领取三个入口改写；
  - 开始后的编辑校验、名单解析、统计扩展。
- `src/app/webapp/routers/gift_pack.py`：新增名单解析端点、开始私信的扫描任务。
- `src/app/main.py`：注册开始私信的扫描任务。

**前端**

- `GiftPackAdminPanel.vue`：受众与领取条件两个编辑器（添加条件、添加「满足其一」组、时间范围与附加参数、名单粘贴与解析结果），任务截止、任务提醒上限、开始通知开关，开始后的只读与放宽约束。
- `GiftPackDialog.vue`：`in_progress` 状态、逐项进度与「或」组展示、「仅可领取」阶段的说明、计数时间范围的文案。
- `GiftPackPromptDialog.vue` / `App.vue`：汇总弹窗分为「可以领了」与「进行中」两块。
- `services/giftPackService.js`：名单解析接口。

**依赖**

- 与 `expand-gift-pack-rewards` 基本独立，仅复用其奖励类型登记表中的「是否需要绑定」属性（自动补绑定条件）。
- 若本变更先落地，这里的绑定判断暂时沿用「含 Premium 天数奖励」的规则。
