# Spec Delta

## Purpose

约定管理员如何把一个用户的全部账号和数据，从旧 Telegram ID 迁到新 Telegram ID：新 ID 可以是全新的，也可以已经有数据。迁移要么完整生效，要么完全不生效，而且在不同数据库上的结果一致。

## ADDED Requirements

### Requirement: 以 Telegram 身份为单位换绑

系统 SHALL 以 Telegram 身份为单位执行换绑。管理员可以用旧 Telegram ID、Plex 邮箱或 Emby 用户名定位旧身份；按邮箱和用户名定位时不区分大小写。定位到旧身份后，旧 ID 名下的全部 Plex、Emby、Overseerr 账号，以及以该 ID 记录的全部业务数据，SHALL 一起迁到新 ID。

换绑完成后，系统中 SHALL NOT 再有任何数据以旧 ID 作为用户标识。

#### Scenario: 按一个媒体账号定位

- **WHEN** 旧 ID 同时绑定了 Plex 和 Emby，管理员只提供 Plex 邮箱执行换绑
- **THEN** Plex 和 Emby 账号都改为绑定新 ID

#### Scenario: 按邮箱定位时忽略大小写

- **WHEN** 管理员提供的 Emby 用户名与存储的大小写不同
- **THEN** 系统仍能定位到该账号

#### Scenario: 找不到账号

- **WHEN** 管理员提供的旧 ID、邮箱或用户名找不到对应的账号
- **THEN** 系统不做任何改动，并说明找不到账号

### Requirement: 迁移全部存储位置

换绑 SHALL 迁移每一处记录该用户 Telegram ID 的数据，包括：

- 积分、捐赠额、锦标赛钱包余额、21 点连败计数和免费转盘进度。
- 勋章、礼包领取状态、转盘免费次数和转盘统计。
- 21 点手牌、锦标赛报名、周返水。
- 夺宝参与、预言投注与投稿、竞拍出价与成交记录。
- 邀请码归属、线路调度、自建线路、捐赠登记、加密货币订单、Vaultwarden 兑换记录。
- 以文本形式记录的 ID：积分兑换邀请码时记录的 `credits_by_<ID>`，以及礼包受众名单中的 ID。
- 管理员操作的审计记录：创建人、审核人、处理人、开奖人等。

迁移 SHALL NOT 依赖数据库的级联更新。同样的数据，在打开或关闭外键约束的 SQLite 上，以及在 PostgreSQL 上换绑，结果 SHALL 相同。

#### Scenario: SQLite 未开启外键

- **WHEN** 在未开启外键约束的 SQLite 上把一个有勋章、21 点手牌和礼包领取记录的用户换到新 ID
- **THEN** 这些记录全部归到新 ID，结果与在 PostgreSQL 上执行相同

#### Scenario: 文本形式的 ID

- **WHEN** 旧 ID 曾把邀请码兑换成积分，并且出现在某个礼包的受众名单里
- **THEN** 邀请码记录的兑换人改为 `credits_by_<新 ID>`，礼包受众名单中的旧 ID 改为新 ID

#### Scenario: 管理员审计记录

- **WHEN** 旧 ID 是一位创建过礼包、审核过自建线路的管理员
- **THEN** 这些记录的创建人和审核人改为新 ID

### Requirement: 换到全新 ID

新 ID 在系统中还没有任何数据时，换绑 SHALL 把旧 ID 的全部数据原样迁到新 ID；各项余额和计数都与换绑前的旧 ID 相同。

#### Scenario: 换到全新 ID

- **WHEN** 旧 ID 有 120 积分、锦标赛钱包余额 30，新 ID 从未使用过
- **THEN** 新 ID 有 120 积分和钱包余额 30，旧 ID 不再有任何数据

### Requirement: 合并到已有 ID

新 ID 已经有数据时，换绑 SHALL 把两边的数据合并到新 ID：

- 积分、捐赠额、锦标赛钱包余额、21 点连败计数和免费转盘进度，按两边的数值相加。
- 不存在唯一冲突的记录，直接归到新 ID。
- 合并后，超出每人上限的情况（例如同一期夺宝的参与份数）只约束之后的操作，不回溯处理已有记录。

#### Scenario: 余额相加

- **WHEN** 旧 ID 有 50 积分、捐赠额 10，新 ID 有 70 积分、捐赠额 5，两边没有冲突
- **THEN** 新 ID 有 120 积分、捐赠额 15，旧 ID 不再有任何数据

### Requirement: 冲突时整体拒绝

合并前，系统 SHALL 先检查以下冲突；只要存在任意一项，SHALL 整体拒绝，不做任何改动，并列出全部冲突：

- 两边持有同一枚勋章。
- 两边都有同一个礼包的领取状态。
- 两边都有同一周的返水记录。
- 两边都报名了同一场锦标赛。
- 两边都有 Overseerr 账号。
- 新 ID 已经绑定了与旧身份同类的 Plex 或 Emby 账号。

#### Scenario: 同一枚勋章

- **WHEN** 旧 ID 和新 ID 都持有同一枚勋章
- **THEN** 换绑被拒绝，两边的数据都不变，输出中列出这枚勋章

#### Scenario: 多项冲突一起列出

- **WHEN** 两边同时存在礼包领取状态冲突和 Overseerr 冲突
- **THEN** 输出中同时列出这两项冲突，而不是只列出第一项

### Requirement: 21 点在途时拒绝

旧 ID 有未结束的 21 点手牌，或者报名了处于报名中、进行中的锦标赛时，系统 SHALL 拒绝换绑，不做任何改动，并提示稍后重试。

其他在途记录 SHALL 照常迁移，之后按新 ID 结算。这些在途记录包括：竞拍出价、尚未开奖的夺宝和预言、待处理的捐赠登记和加密货币订单、待审核的自建线路。

#### Scenario: 有进行中的手牌

- **WHEN** 旧 ID 有一手尚未结算的 21 点
- **THEN** 换绑被拒绝，并提示存在进行中的 21 点

#### Scenario: 未开奖的预言投注

- **WHEN** 旧 ID 有尚未开奖的预言投注，换绑成功后该市场开奖
- **THEN** 奖金结算给新 ID

### Requirement: 换绑未绑定 Telegram 的媒体账号

定位到的媒体账号还没有绑定 Telegram ID 时，系统 SHALL 按绑定规则处理：

- 确保新 ID 有积分账户。
- 把该账号在未绑定期间积累的积分转入新 ID。

新 ID 已经绑定了同类账号时，SHALL 拒绝。

#### Scenario: 未绑定账号的积分

- **WHEN** 一个未绑定 Telegram 的 Plex 账号有 8 积分，管理员把它换绑到新 ID
- **THEN** 该账号改为绑定新 ID，新 ID 的积分增加 8，账号上的未绑定积分归零

### Requirement: 换绑是原子操作

整个换绑 SHALL 在一个事务中完成。任何一步失败，包括数据库错误，SHALL 回滚全部改动，两个 ID 的数据都与换绑前相同。

#### Scenario: 中途失败

- **WHEN** 换绑进行到一半时发生数据库错误
- **THEN** 两个 ID 的全部数据都保持换绑前的状态，命令报告失败原因

### Requirement: 手动命令

系统 SHALL 提供命令 `python -m app.manage rebind-tg-id`，参数如下：

- 必填：新 ID。
- 旧身份的定位方式三选一：旧 ID、Plex 邮箱、Emby 用户名。
- 可选：`--dry-run`。

命令的行为：

- 成功时，按领域输出迁移的记录数，退出码为 0。
- 失败时，输出失败原因，例如找不到账号、冲突清单或在途的 21 点，退出码非 0。
- `--dry-run` 模式下，完整执行一遍检查和迁移，然后回滚；输出与真实执行相同的计数或失败原因，数据库不变。
- 旧 ID 在管理员配置中时，命令 SHALL 输出提示，要求运维手动更新部署配置。

#### Scenario: 演练模式

- **WHEN** 管理员带 `--dry-run` 执行一次本应成功的换绑
- **THEN** 输出各领域将要迁移的记录数，数据库中的数据不变

#### Scenario: 旧 ID 是管理员

- **WHEN** 被换绑的旧 ID 在管理员配置中
- **THEN** 换绑正常完成，输出中提示需要把部署配置里的旧 ID 改为新 ID

### Requirement: 换绑后缓存反映新 ID

换绑提交后，系统 SHALL 让被迁移媒体账号的用户信息缓存反映新 ID，并让受影响账号的积分缓存失效。换绑失败或演练模式下，缓存 SHALL 保持不变。

#### Scenario: 用户信息缓存

- **WHEN** 换绑成功提交
- **THEN** 网关读到的这些媒体账号的用户信息中，Telegram ID 是新 ID
