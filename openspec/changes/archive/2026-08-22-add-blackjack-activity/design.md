## Context

动机见 `proposal.md` 的 Why。需求契约见 `specs/blackjack/spec.md`。本文只记录实现取舍。

塑造设计的现有约束：

- **活动路由分层已定型**：`src/app/webapp/routers/activities/` 下每个活动一个模块，业务逻辑下沉到 `db.py`，路由只做参数校验、异常翻译与通知编排。四个既有活动无一例外。
- **`db.py` 已达 8300 行**，是单一 `DatabaseORM` 单例。新活动的 DB 方法必须加进去（项目约定「所有 DB 操作住在 `DatabaseORM`」），但纯计算逻辑不应进去。
- **会话管理只有一种形态**：`get_session()` 上下文管理器自动 commit/rollback，全部同步 SQLAlchemy。跨请求的事务不存在。
- **积分并发的既有范式**：`select(Statistics).where(...).with_for_update()`，见 `db.py` 的夺宝与大预言家结算。
- **既有活动的配置存储**：`SystemConfig` 表按 `(config_type, config_key)` 存 JSON 字符串，`get_lucky_wheel_config` / `set_lucky_wheel_config` 是薄封装（`db.py:5993`）。
- **持久化延时任务已有先例**：`treasure.py:76` 的 `Scheduler().add_async_job(..., jobstore="sqlalchemy")`。
- **无限流中间件**：`middlewares.py` 只有 `TelegramAuthMiddleware`。无 slowapi 等依赖。
- **数据库目标为 SQLite 与 PostgreSQL**。（MySQL 虽在 `config.py` 中列出且有 `[mysql]` extra，但从未被测试；其移除由 `drop-mysql-support` 变更处理。本设计不依赖 MySQL 特性，也不依赖仅 PostgreSQL 具备的特性，故两个变更的落地顺序互不影响。）
- **`Statistics.credits` 是 `Float`**，全项目以 `round(x, 2)` 收敛。

## Goals / Non-Goals

**Goals:**

- 手牌规则逻辑与积分副作用彻底分离，使规则可被独立测试、并为 Phase 2 换用赛内筹码留出替换点
- 结算的原子性：扣分、发牌、判定、赔付、抽水拆分在单一事务内完成，任何中途失败都不留下「已扣分未结算」的状态
- 服务端不可中途换牌，且任一已结束手牌可复现
- 在 SQLite 与 PostgreSQL 上行为一致，不依赖单一数据库的方言特性

**Non-Goals:**

- 不追求实时性（无 WebSocket/SSE，项目也没有这套基础设施）
- 不做基本策略提示、算牌检测、连胜统计
- 不实现 Phase 2 争霸赛的任何运行时逻辑——只留接缝
- 不为用户提供牌序查验入口（见 spec「牌靴定序的不可篡改性」）

## Decisions

### 决策 1：三层切分，规则引擎为纯函数

```
┌──────────────────────────────────────────────────────────┐
│  routers/activities/blackjack.py                          │
│  参数校验 · 权限 · 异常翻译 · 超时任务编排                  │
└───────────────────────┬──────────────────────────────────┘
                        │
┌───────────────────────▼──────────────────────────────────┐
│  db.py 中的 blackjack_* 方法（结算适配层）                 │
│  事务边界 · FOR UPDATE 锁 · 积分读写 · 抽水拆分 · 幸运奖池  │
└───────────────────────┬──────────────────────────────────┘
                        │ 调用，传入牌面与动作，取回倍率
┌───────────────────────▼──────────────────────────────────┐
│  blackjack_engine.py（纯函数，无 IO、无积分概念）          │
│  牌靴定序 · 点数计算 · 动作合法性 · 庄家补牌 · 胜负与倍率   │
│  基本策略建议 · 奖池触发牌型判定                            │
└──────────────────────────────────────────────────────────┘
```

**引擎返回赔付倍率，不返回积分数。** 这是 Phase 2 的关键接缝：倍率 × 注额 → 积分的换算发生在适配层，Phase 2 只需换一个适配层把倍率作用于赛内筹码，引擎一行不动。

引擎返回 `(return_multiplier, profit_multiplier)` 二元组而非单一数字——适配层用 `profit_multiplier` 算抽水、用 `return_multiplier` 算入账。两者均相对**基础**注额 `B`：

| 情形 | 总押注 | `return_multiplier` | `profit_multiplier` |
|---|---|---|---|
| 判负 | `B` | 0 | 0 |
| 平局 | `B` | 1 | 0 |
| 普通胜 | `B` | 2 | 1 |
| 天胡胜 | `B` | 2.5 | 1.5 |
| 加倍后判负 | `2B` | 0 | 0 |
| 加倍后平局 | `2B` | 2 | 0 |
| 加倍后胜 | `2B` | 4 | 2 |

加倍胜是最易错的一格：总押注 `2B`，胜时返还本金 `2B` 加赢利 `2B`，故 `return_multiplier = 4`。用二元组而非单值，正是为了让这一格不产生歧义。

**为什么不把引擎放进 `db.py`**：`db.py` 已 8300 行，且引擎是唯一可以脱离数据库单测的部分。项目当前无测试套件（`AGENTS.md` 明确说明），但纯函数引擎是将来最值得补测试的地方——把它做成可测的形状，成本为零。

替代方案：全部塞进 `db.py` 一个大方法。否决——规则与事务纠缠后，Phase 2 必须重写，且无法在不起数据库的情况下验证「A、A 应为 12 点」这类判定。

### 决策 2：牌靴用种子推导，只存种子与游标

`blackjack_hand` 存 `deck_seed` 与 `next_card_index`，**不存牌靴数组**。取第 N 张牌 = 用种子重建牌序后取下标 N。

牌序生成：`random.Random(seed_int)` 做 Fisher-Yates。`seed_int` 来自 `secrets.token_bytes(16)`（`secrets` 已在 `luckywheel.py` 中使用）。

- **确定性**：同种子恒得同牌序，满足「争议可复现」
- **不可中途换牌**：牌序在发牌时由种子锁定，`next_card_index` 只增不减；服务端要换牌就得改种子，而种子在发牌时已落库
- **省存储**：一手牌只多两个字段，而非一个 52 元素数组

**为什么用 `random.Random` 而不是 `secrets.SystemRandom`**：后者不可复现（无法设种子），与「争议可复现」直接冲突。种子本身来自 `secrets`，所以牌序不可预测；洗牌算法只需确定性，不需要密码学强度。这一点与转盘不同——转盘不需要复现，所以它用 `SystemRandom` 是对的。

**牌靴规格**：单副 52 张，每手重新定序（spec 已规定手牌间不延续）。单手最多用到十余张，52 张足够；用多副牌只会增加实现负担而不改变任何可观察行为。

替代方案：每次要牌现场 `secrets.randbelow`。否决——丢失复现能力，且无法证明服务端没有在要牌时挑牌。

### 决策 3：「同时只有一手」用状态查询 + 行锁，不用 partial unique index

原本的直觉方案是 `UNIQUE INDEX ... WHERE status IN (1,2)`。**否决**：SQLite 与 PostgreSQL 的部分索引语法不同（SQLAlchemy 的 `Index(..., sqlite_where=/postgresql_where=)` 需要分别声明），而 `models.py` 现有 8 处 `UniqueConstraint` 全是普通约束，引入方言特有索引会成为该文件里唯一的特例。

改为：发牌时在事务内先 `SELECT ... WHERE tg_id=? AND status IN (1,2)` 检查，命中则拒绝。为防并发双开，对该用户的 `Statistics` 行取 `with_for_update()` —— **发牌本来就要锁这行来扣积分**，顺带获得了「同一用户的发牌请求串行化」，无需额外锁对象。

这个手法有个额外好处：它同时挡住了「并发发牌绕过速率限制」和「并发发牌绕过门槛校验」，三个问题一把锁解决。

### 决策 4：速率保护读数据库，不用 Redis

`RedisCache.put` 内部是 `SET key value ex=ttl`（`cache.py:293`），**没有 `NX` 参数**，无法做原子占位；要加 `NX` 就得改公共缓存类或绕过封装直接用 `redis_client`。

而正确答案更简单：**发牌时已经在读该用户的手牌了**，顺手取其最近一手的 `created_at_ms`，与当前时间比较即可。同一事务、同一把锁、零额外依赖、且判定可靠（不会因缓存失效而失效）。

这也让 spec 里原本那条「速率存储不可用则放行」的场景变得不必要——已相应删除。

### 决策 5：结算在单一事务内完成，抽水拆分与奖池派彩同事务

结算路径（停牌 / 加倍 / 爆牌 / 超时兜底 共用）：

```
BEGIN
  UPDATE hand SET status=2 WHERE id=? AND status=1   ← 原子抢占，见下
  SELECT statistics FOR UPDATE
  引擎推进庄家补牌 → 得胜负与倍率
  算 gross_profit = profit_multiplier × bet
  算 rake = round(gross_profit × rake_bp/10000, 2)   (仅 gross_profit > 0)
  算 payout = round(return_multiplier × bet − rake, 2)
  SELECT system_config(blackjack, jackpot_fund) FOR UPDATE
  判定奖池触发牌型 → 算 jackpot_won，扣减奖池余额
  jackpot_fund += round(rake × rake_jackpot_bp / rake_bp, 2)
  statistics.credits += payout + jackpot_won
  写回 hand：status=已结算, outcome, payout, rake, jackpot_won,
            decisions_*, 庄家牌面, settled_at
COMMIT
```

奖池的**派彩与累积在同一次加锁内完成**，顺序是先派后累——同一手牌不应吃到自己刚交的抽水。

**幂等闸门是第一步而非最后一步**：这句话必须按字面执行——闸门要在**任何写操作之前**，而不只是在结算函数的开头。

每个改动手牌的动作（要牌/停牌/加倍/超时结算）都以一次**原子抢占**开始：

```
UPDATE blackjack_hand SET status=2 WHERE id=? AND status=1
```

`rowcount == 0` 即放弃，不做任何写入。抢到的一方独占该手牌，之后才扣分、发牌、结算。`status=2`（庄家回合）同时充当独占标记与 spec 所述的中间状态，只在事务内可见，回滚即恢复为 1；要牌未爆时再由 `_release_blackjack_hand` 交还状态 1。

**为什么闸门必须早于写操作**：曾把闸门放在结算函数内部（终态写入时才 CAS），结果加倍会先扣掉一份注额、要牌会先写入一张新牌，而随后的 CAS 可能失败——事务仍会提交那些写入，造成**扣了钱不赔付**，以及**牌面与 outcome 不一致**（3 张牌的爆牌手记着按 2 张牌算出的 push），后者还破坏了「凭种子完整复现」的前提。

终态写入本身仍带 `WHERE status NOT IN (终态)` 作为第二道防线。

**奖池的首次注入需额外处理**：`SELECT … FOR UPDATE` 对**尚不存在的行**锁不到任何东西（PostgreSQL 亦然），两个并发事务会各自认为需要 INSERT 而撞上 `uq_config_type_key`。故插入放在 SAVEPOINT 内，撞约束时回退到「重新读取 + 累加」，使先到者的注入不被丢弃。

**加锁顺序统一为 hand → statistics → system_config**。发牌路径因此**只锁 statistics 而不锁手牌行**：它已持有 statistics，若再锁手牌就与超时任务构成 ABBA 死锁（超时任务持有手牌等 statistics）。同一用户的手牌读取由 statistics 锁间接串行化，无需另外加锁。

**惰性清理独立成事务**（`sweep_timed_out_blackjack_hands`）：若寄生在发牌事务里，发牌后续任何一次校验失败（速率、门槛、余额）都会把已完成的结算连带回滚，丢弃用户的赔付。独立事务先行提交后，发牌被拒也不影响它。该方法同时供 `GET /current` 与定时兜底任务调用，使查询路径自身保持只读。

**销毁部分不需要落账**：销毁即「不发给任何人」，`rake` 中未进奖池的部分自然消失。只需在手牌上记录 `rake_credits` 供审计。这与大预言家一致（`db.py` 的 `fee_burned` 只是记录字段）。

### 决策 6：每手牌快照发牌时的参数

spec 要求「配置变更不影响进行中手牌」。实现方式：发牌时把当次生效的 `rake_bp_on_profit`、`rake_glory_bp`、`blackjack_payout`、`dealer_hits_soft_17` 一并写入手牌行，结算时读手牌上的快照而非读当前配置。

代价是几个冗余列。收益是结算逻辑不依赖「配置在手牌存续期间没被改过」这个无法保证的前提，且已结算手牌可被完整复现（配合种子）。

### 决策 7：超时兜底三层保障，不把正确性押在调度器上

发牌后 `Scheduler().add_async_job(..., trigger="date", jobstore="sqlalchemy", id=f"blackjack_timeout_{hand_id}", replace_existing=True, misfire_grace_time=None)`。

`misfire_grace_time=None` 是必需的：调度器全局默认只有 60 秒（`scheduler.py`），一次超过一分钟的重启就会让 APScheduler 判定任务错过而**永久丢弃**它。

三层保障，缺一不可：

| 层 | 机制 | 覆盖的情形 |
|---|---|---|
| 及时性 | 持久化的 date 任务 | 正常运行 |
| 重启恢复 | `restore_blackjack_timeouts()`（照 `auction.restore_auction_schedules`） | 重启后重建仍在进行中的手牌的任务 |
| 最终一致 | `sweep_expired_blackjack_hands_job()` 每 10 分钟全量扫描 | 任务因任何原因丢失，或用户再也不回来 |

发牌与 `GET /current` 时按用户做的惰性清理是便利而非保障——它只在该用户自己再次操作时触发。**若用户再也不回来，只有全量兜底能救**，否则手牌会带着已扣的押注永久悬挂，违反 spec「超时任务 SHALL 持久化，服务重启 SHALL NOT 导致待处置的手牌被遗漏」。

### 决策 8：抽水改注入自有的幸运奖池，不再进荣耀奖池

**原方案**是沿用 `(config_type='prediction_market', config_key='glory_fund')`，把 40% 的抽水注入大预言家的荣耀奖池。**已推翻**：从 21 点玩家的视角，那是一笔完全看不见的税——他付了抽水，却只在另一个活动的特定结算情形下才会被别人用掉。

改为注入**本活动自有的幸运奖池**（`(config_type='blackjack', config_key='jackpot_fund')`），余额在牌桌上可见。同一笔钱，从隐形税变成看得见的胡萝卜，且经济学上更干净：奖池只由抽水供养，不增发积分，21 点对全站积分总量的影响仍是净回收。

**荣耀奖池自此与 21 点无关**，`db.py:2213` 的大预言家结算不受本变更影响。已实现的荣耀奖池浮点化保留——它修掉的是「`int()` 读到小数即抛错、余额被静默清零」这个既有隐患，与 21 点是否注入无关，属于独立的健壮性改进。

**触发条件必须够稀有，否则奖池攒不起来。** 实测算过稳态规模（抽水的 40% 入池，日均 200 手）：

| 触发 | 频率 | 稳态奖池（注 5 / 15 / 30） | 间隔 |
|---|---|---|---|
| 天胡 | 4.83% | 0.6 / 1.9 / 3.7 | 每天数次 |
| 同花天胡 | 1.21% | 2.5 / 7.4 / 14.9 | 约 0.4 天 |
| 三张 7 | 0.018% | 165 / 495 / 990 | 约 28 天 |

以天胡为触发的奖池只有个位数积分，起不到任何吸引作用。故采用**双层触发**：

- **同花天胡 → 派发余额的 10%**：约 83 手一次，金额小但让用户经常看到「奖池真的会发出去」，奖池也因此永不清零
- **三张 7 → 派发全部余额**：约 5525 手一次，是真正的大奖

两者互斥（同花天胡是初始两张，三张 7 是三张牌），无需定义优先级。

**派彩独立于本手胜负**：拿到三张 7 却因庄家天胡判负仍照发。反过来做会让最稀有的牌型有概率颗粒无收，体验极差，而这恰恰是最需要正反馈的时刻。

**派彩单独记账**（手牌上的 `jackpot_won` 列），不并入 `payout_credits`。否则单手最大赢利榜会退化成奖池中奖者名单，那个榜就没有意义了。

奖池的存储与并发沿用荣耀奖池已验证的那套：`SystemConfig` 存小数字符串，`SELECT … FOR UPDATE` + 首次插入放 SAVEPOINT 内以避开「对不存在的行加不到锁」的竞争。派彩与累积在同一次结算事务内完成。

### 决策 9：数据模型

```
blackjack_hand
├─ id                    BIGINT   PK
├─ tg_id                 BIGINT   索引
├─ status                SMALLINT 1=玩家回合 2=庄家回合 3=已结算 4=超时弃牌
├─ bet_credits           INTEGER  基础注额
├─ doubled               SMALLINT 0/1
├─ deck_seed             TEXT     ← 绝不出现在面向用户的响应中
├─ next_card_index       INTEGER
├─ player_cards          TEXT     JSON 数组
├─ dealer_cards          TEXT     JSON 数组（玩家回合期间响应层须裁剪）
├─ outcome               TEXT     win / lose / push / blackjack / bust
├─ payout_credits        FLOAT    ← 不含奖池派彩
├─ rake_credits          FLOAT
├─ jackpot_won           FLOAT    NULL  奖池派彩，单独记账不并入 payout
├─ decisions_total       INTEGER  本手的决策次数
├─ decisions_correct     INTEGER  其中与基本策略一致的次数
├─ rake_waived           SMALLINT 0/1，是否为当日免抽水的那一手
├─ 参数快照：rake_bp_on_profit / rake_jackpot_bp /
│             blackjack_payout / dealer_hits_soft_17 / hand_timeout_minutes
├─ tournament_id         BIGINT   NULL  ← Phase 2 预留，恒为 NULL，无外键约束
├─ created_at_ms         BIGINT   索引（兼作速率判定与当日首手判定的依据）
├─ created_at            DateTime 索引
└─ settled_at            BIGINT   NULL
```

索引：`(tg_id, status)` 支撑「找进行中手牌」，`(tg_id, created_at_ms)` 支撑速率判定、当日首手判定与各榜单。

`decisions_total` / `decisions_correct` 落在**手牌**而非用户上：与快照同一哲学——每手牌自带其评判依据（当时的庄家规则），用户维度的准确率由聚合得到，不需要额外维护一份可能与明细不一致的累计值。

`rake_waived` 与「快照 `rake_bp_on_profit=0`」信息重复，但仍单列：管理员把全局抽水调成 0 时两者会混淆，显式一列让审计无歧义。

`tournament_id` 现在就加（可空、无外键、无索引），Phase 2 建锦标赛表时不必改已有表、不必写数据迁移。一列的成本换掉一次将来的 migration。

### 决策 12：基本策略表放在引擎，与胜负判定同层

判定「玩家这一手该不该要牌」是一个纯函数：入参为玩家牌面、庄家明牌、是否还能加倍、庄家软 17 规则，出参为建议动作。没有 IO、没有积分概念，与 `resolve()` 完全同构，因此放进 `blackjack_engine.py`。

这带来两个直接好处：**可脱离数据库单测**（项目当前无测试套件，但这是最值得补测试的地方），以及**零方差**——同一局面的建议恒定，故决策准确率是这个游戏里唯一完全不受运气影响的指标，这正是它适合当主榜的原因。

采用标准的「不分牌、不投降、不保险」基本策略表，依据手牌快照的 `dealer_hits_soft_17` 在 S17 与 H17 两套之间切换（两者只有少数几格不同）。加倍不可用时（手中已超过两张），建议自动回退为要牌或停牌。

**只评判、不干预**：spec 明确系统不阻止玩家做非最优决策。把它做成事后反馈而非事前拦截，既尊重玩家，也避免把游戏变成照表操作。

### 决策 13：免抽水复用参数快照，结算逻辑一行不改

发牌时若判定为当日首手，直接把快照列 `rake_bp_on_profit` 写成 0。结算读的本来就是快照，于是 `rake = round(gross_profit × 0 / 10000, 2) = 0` 自然成立——**不需要在结算路径上加任何分支**。

当日首手的判定用 `created_at_ms >= 当日零点（settings.TZ）`，走已有的 `(tg_id, created_at_ms)` 索引，不新增存储也不新增查询模式。

替代方案：在结算处加一个 `if hand.rake_waived: rake = 0`。否决——结算路径是本变更里最该保持简单的地方，能用既有机制表达的就不该新增分支。

### 决策 10：前端信息隐藏在 schema 层强制

响应模型不复用手牌行的 dump。`BlackjackHandResponse` 显式列字段，`deck_seed` 与 `next_card_index` 根本不在模型里；`dealer_cards` 在玩家回合时由构造函数裁剪为仅首张。

**不依赖「路由里记得过滤」**——那是最容易在后续改动中被绕过的写法。把裁剪放在响应模型的构造入口，任何路径都得经过它。

### 决策 11：游戏王勋章取「2000 手 + 决策准确率 ≥ 80%」双条件

手数基准是大转盘的 5000 次 × 10 积分 = 5 万积分投入量。21 点按平均注额 15 计，等价投入量约 3300 手；按最小注 5 计约 1 万手。取 **2000 手**，略低于等价投入量——21 点单手需多次交互，耗时显著长于转盘一次点击，若按投入量对等设到 3300 手以上，该条件会形同虚设。

**但单以手数为条件是个纯粹的刷量激励，而这是一个负期望的游戏。** 2000 手 @ 注 15 的期望代价是 −720 积分（2000 × 15 × 2.4%）。这个价格本身不算贵（对照：大转盘 5000 次的期望代价是 −37500 积分），问题在于它奖励的行为是「多打」而不是「打好」。

叠加 **决策准确率 ≥ 80%** 后，这条件奖励的变成了「把牌打好」。80% 是一个刻意留出余地的阈值：严格照基本策略打是 100%，凭直觉打的普通玩家大约在 70–85% 之间，故它可达但需要用心，且天然把「乱按一气刷手数」挡在外面。

两个阈值都写在 `db_func.py` 勋章检查处的常量里，与既有的 `WHEEL_SPIN_THRESHOLD` 等并列，日后调整是一行改动。

## Risks / Trade-offs

- **[引擎与适配层的倍率口径理解偏差导致赔付错误]** → 加倍胜的倍率是最易错处（本金 `2B` + 赢利 `2B`）。用 `(return_multiplier, profit_multiplier)` 二元组消除歧义，并在 spec 的「胜负判定与赔付」中已用具体数字固定了各情形的期望值，实现时逐条对照。

- **[`Float` 积分在 3:2 赔率下产生 `.5` 尾数，累积舍入偏差]** → 天胡赔率使注 5 的赢利为 7.5，抽水后为 7.28 之类。全路径统一 `round(x, 2)`，与项目既有做法一致。注额档位 5/15/30 中 15 与 30 的 1.5 倍为整数，仅 5 会产生 7.5，偏差量级可忽略。

- **[荣耀奖池浮点化触及已上线的大预言家结算]** → 见决策 8。改动限于数值域（`int` → `float` + `round(x, 2)`），分发逻辑与比例计算一行不动；既有整数字符串余额可被 `float()` 直接读入，无数据迁移。该改动现已与 21 点解耦（21 点不再注入该池），保留是因为它独立地修掉了「读到小数即静默清零」的既有隐患。

- **[幸运奖池规模与手数量线性相关，冷清社区里奖池长期偏低]** → 稳态奖池 ≈ 触发间隔手数 × 每手抽水的奖池份额。社区活跃度低时，777 可能数月才出一次且金额有限。缓解：双层触发保证同花天胡这一档每天都在发放，用户看得到奖池在动；管理员可手动注入种子余额启动冷场。若长期偏低，可调高奖池分成（`rake_jackpot_bp`）——上限是抽水全额，仍不增发积分。

- **[决策准确率成为勋章条件后，可能诱发「照表操作」而非享受游戏]** → 这正是意图：把刷量激励换成打好激励。阈值取 80% 而非 100%，留出凭直觉打也能达标的空间，避免逼所有人对着策略表点鼠标。

- **[基本策略表实现错误会同时污染反馈、榜单与勋章三处]** → 它是纯函数且零方差，是本变更里最容易也最值得单测的部分。实现时逐格对照标准 S17 表，并对若干代表性局面（16 vs 10、A7 vs 3、11 vs A、软手不可加倍时的回退）写明确用例。

- **[SQLite 下 `with_for_update()` 是 no-op，行锁无法保证幂等]** → 原以为「SQLite 写操作串行化，实际效果等价」，**实测证伪**：两个并发停牌事务可以各自读到 `status=1`、各自算出赔付、再依次写入，造成重复赔付（8 并发下复现，积分被加了两次）。改为**不依赖行锁的条件 UPDATE（compare-and-swap）**：终态写入带 `WHERE status NOT IN (终态)`，只有 `rowcount == 1` 的一方才继续计入积分与注入奖池。这在 SQLite 与 PostgreSQL 上都成立，也不再依赖任何方言特有的锁语义。`with_for_update()` 保留在读取处，PostgreSQL 上仍能减少无谓的重算。

- **[惰性清理使超时手牌的结算时点晚于名义时限]** → 若调度任务正常，时限即生效；仅在调度丢失时才由下次发牌触发。用户感知上是「上一手牌延迟结算了」，积分结果与按时结算完全相同（庄家补牌是确定性的，与结算时刻无关）。

- **[不限手数使 DB 行数随活跃度线性增长]** → 负 EV 加门槛 30 构成吸收壁，用户积分存量本身限制了总手数；1 秒速率下限压制脚本。若日后行数成为问题，可加归档任务，不影响本设计。

- **[规则说明写死在前端，与后端配置漂移]** → 赔率、注额档位、门槛、抽水比率均从配置接口取值后渲染，不在前端硬编码数字；仅动作说明与庄家规则等结构性文案为静态。

## Migration Plan

1. Alembic 迁移建 `blackjack_hand` 表（纯新增，无既有表变更，无数据迁移）
2. 后端上线；活动默认**停用**（服务端开关），仅管理员可见配置面板
3. 管理员写入首份配置，小范围试玩，核对：抽水计取、免抽水手、幸运奖池增量与双层派彩、决策评判、超时兜底、加倍余额校验、并发双开防护
4. 前端启用 21 点卡片并调整列表顺序至大转盘之后
5. 榜单与勋章条件最后接入（依赖已有真实手牌数据才能验证排序口径）

**回滚**：服务端开关置为停用即可停止新发牌，进行中手牌仍能正常结算完（spec 已规定）。表可保留，无需回退迁移。幸运奖池的余额不回滚——它由抽水惰性累积，停用后只是不再增长，不影响正确性。

**幸运奖池的冷启动**：上线时余额为 0，需要积累若干手才有观感。可由管理员在配置面板手动写入一笔初始余额作为种子——这是本设计里唯一会增发积分的路径，故必须是管理员显式操作而非自动行为。
