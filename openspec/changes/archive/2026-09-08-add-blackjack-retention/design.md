# Design: add-blackjack-retention

## Context

21 点结算核心为 `db._settle_blackjack_hand`（`src/app/databases/db.py:3123`），四条结算路径（停牌/加倍/爆牌/超时）汇入一处，CAS 条件 UPDATE 保证幂等；锦标赛经 `_settle_blackjack_tournament_hand` 适配层隔离。大转盘为 `system_config` 表 `config_type="lucky_wheel"` 的**线上可调配置**，`execute_single_spin`（`src/app/webapp/routers/activities/luckywheel.py:259`）扣费→抽取→入账，负奖品截断至 0。**线上实际奖池不含翻倍/减半，已替换为 ±100 固定积分**（代码内置默认配置仍含翻倍/减半，以线上配置为准）。锦标赛报名费 `buy_in_credits` 从积分扣除，取消时全额退回积分。用户积分存于 `statistics.credits`。

动机见 proposal.md — Why。本设计回答三个机制如何挂在既有骨架上、参数如何由经济模型推导、以及如何防止让利被刷成正期望。

## Goals / Non-Goals

**Goals**

- 三个机制全部复用既有结算核心、调度器与配置体系，不新增服务或外部依赖。
- 全部参数在线可调，附成本模型，管理员可按表核算任一参数变动的影响。
- 主力注额（15/30 分）玩家画像下 21 点整体仍为清晰的负期望；任何刻意刷量的绝对收益被周上限封顶在个位数（每周）。

**Non-Goals**

- 不做专用小转盘 / 新奖池配置 / 转盘道具化交易。
- 不做 XP、等级、任务、赛季（若本期效果不足，另立 change）。
- 不改单手规则、赔率、抽水结构与幸运奖池机制。
- 不追求「任意注额任意余额严格负期望」的数学闭式——低注玩家的轻度让利被接受（见 D1 论证），以周上限控制绝对敞口。

## Decisions

### D1. 让利预算与默认参数的推导（本设计的核心）

**结构性抽耗**（基本策略玩家，注额 b）：规则边际 ≈ 0.9%（无分牌 +0.53%、后投降 −0.07%、S17 基线 0.45%）+ 净赢抽水 3% ≈ 1.35%，合计 ≈ **2.25%×b/手**。休闲玩家实际 3%~5%。

**转盘单次 EV（线上 ±100 奖池）随余额分布**：

| 使用时余额 | 截断效应 | EV |
|---|---|---|
| ≥ 100 | 无 | **+2.8** 固定，与余额无关 |
| 30 ~ 100 | −50/−100 被截断，少亏 | +3.8 ~ +4.5 |
| → 0 | 全部负奖品截断 | +11.5（仅回流场景，无法主动刷：获取需 ≥30 余额打满手数） |

翻倍/减半改为 ±100 后，「EV 随余额无界放大」消失；剩余的余额依赖只有截断保护，且只抬高低余额区（≤ +1.7，有界）。

**三项让利率**（15 分注，手数阈值 20，周上限 5）：

| 机制 | 公式 | 让利/手 | 占抽耗比 |
|---|---|---|---|
| 连败救济 | P(连败至第 8 手)×1×b ≈ 0.527⁷×0.473×b | 0.53%×b | 23% |
| 周损失返还 | 15% × (抽耗 − 救济) | 0.26%×b | 11% |
| 免费转盘 | EV(spin) ÷ 手数阈值（未触顶时） | 0.14 ~ 0.22（与注额无关） | 42% ~ 67% |

周上限的作用不是压缩让利率（对已触顶玩家其比例由手数阈值与注额决定，与上限无关），而是决定「谁触顶」与刷量绝对天花板：上限 5 对应每周 100 手全覆盖（日活玩家整周覆盖），5 分注刻意驻留低余额区的刷量天花板约 +15 分/周，仍远低于被动观看收入 8 分/天。上限 7 会使 15 分注玩家在截断区（EV 4.5）的理论让利超过抽耗而翻正，故 5 为安全上界内的默认值。

**为什么手数口径现在可行**：手数的 earning 成本随注额缩放（H×b×2.25%），转盘 EV 与注额无关——严格闭式安全要求 H ≥ 307/b（15 分注需 H≥20.5，5 分注需 H≥62，对全部注额安全的手数阈值不可行）。但 ±100 后该失配的**绝对敞口有界**：周上限 5 把最坏情况（5 分注、驻留 30~100 余额区间刻意刷）封顶在约 +9~+15 分/周，而被动的观看收入是 8 分/天——刷转盘在理性上被完全支配，不存在可行的套利；且低注低余额玩家正是最容易流失、最需要留在牌桌的人群，每周十几分的补贴符合留存目标。主力注额玩家的账目：

| 画像 | 有效期望 |
|---|---|
| 30 分注（重度玩家） | −0.7% ~ −1.0% |
| 15 分注，余额 ≥ 100 | −0.53% |
| 15 分注，余额 30~100（截断区） | ≈ 0%（瞬态区间，玩家要么跌破门槛停止、要么回升脱离） |
| 5 分注 | 轻度净补贴，周封顶 +9~15 分 |

整体仍是回收器：重度玩家失血速度降至原来的 1/4~1/2，休闲玩家降得更慢但仍为负。上表为未触顶的线性让利率，周手数超过 100（周上限×阈值）后转盘让利被截断、有效期望反而更深，故上表即最劣情形。

**与投注流水口径的对比**（备选，被否）：流水阈值 W 使 earning 成本与注额同随缩放，数学上无懈可击（W ≥ 310 即任意画像安全），但 5 分注玩家需 100 手才见一次转盘——功能对该人群不可见，与留存目标冲突；且进度语义（「投注流水 250/500」）不如「打满 20 手」直白。手数口径以有界、被理性支配的轻度敞口换来目标人群的功能可见性，是更优的产品取舍。

**参数护栏**（写入管理端说明）：任一参数或转盘奖池调整后按上表重算，保持「15/30 分注画像合计让利 ≤ 抽耗的 85%」；`手数阈值 ≥ 20`（低于 20 将使 15 分注玩家在截断区翻正）；`周上限 ≤ 5`（7 会使截断区画像翻正）；**若线上奖池重新启用翻倍/减半类随余额放大的奖品，必须立即改回投注流水口径或增设使用余额上限**。

### D2. 连败救济挂在结算核心，同事务记账

在 `_settle_blackjack_hand` CAS 抢占成功、赔付入账之后（约 db.py:3390 积分入账处）同事务执行：读 `statistics` 上的连败计数列 → 按 outcome 更新（判负 +1 / 判胜归零 / 平局与投降不动）→ 达阈值则补偿 `基础注额 × 倍数` 入账并将计数归零 → 补偿额写入 `blackjack_hand.relief_credits` 新列。

- 备选「从 `blackjack_hand` 历史回溯推导计数」被否：每次结算多一次反向扫描，长连败用户扫描成本无界；存储列 O(1)，且 `relief_credits` 落行可对账。
- 加倍手牌触发时按基础注额补偿（spec 已约定），`relief_credits` 与投注额分列不混淆。
- 幂等性继承 CAS：救济随结算原子发生，重试不重复发放。

### D3. 争霸赛余额落 `statistics` 新列 `tournament_wallet_credits`

与 `credits` 同行同事务更新，报名校验与扣款天然一致，无跨行锁。备选独立钱包表被否：报名时需锁两行，收益为零。余额不可提现/兑换/转移，仅报名费可扣（spec 约束），路由层不提供任何其他扣减入口。

### D4. 周结算幂等：`blackjack_weekly_cashback` 表 + UNIQUE 约束

新表 `(tg_id, week_start, net_change, cashback_credits, created_at)`，`UNIQUE(tg_id, week_start)`。调度任务每周一日界（与每日首手免抽水的自然日口径一致，实现时确认既有时区处理）执行：

1. 计算上一完整自然周的 `[start, end)`；
2. 聚合该窗口内 `settled_at` 落入的现金局手牌：`Σ(payout_credits − 投注额 + relief_credits + jackpot_won)`（投注额 = `bet_credits × (1 + doubled)`；`jackpot_won` 存派彩金额）；
3. 逐用户：净变动 < 0 且 |净变动|×比率 ≥ 发放门槛 → INSERT 结算行（冲突即跳过，保证重跑幂等）→ 争霸赛余额入账 → TG 通知（上周净亏损、返还金额、余额用途）。

服务重启后任务重跑：已存在行被 UNIQUE 冲突跳过，不漏不重。上线首个结算周期为启用后的第一个完整自然周（锚点取首次运行时刚结束的完整周，即部署周）。停用期间游标照常推进（与奖池播报游标同款纪律）：停用的周即不结算的周，重启用后不回溯——代价是「启用期某次周一任务没跑 + 随后停用」的那一周会丢失，属可接受的极端角案例。

### D5. 报名支付拆分：报名记录加 `wallet_paid_credits` / `credits_paid_credits`

报名时 `min(wallet, buy_in)` 从争霸赛余额扣、余下从积分扣，两列记录拆分；校验 `wallet + credits ≥ buy_in`。取消退款按拆分原路退回。既有「重复报名/满员/进行中拒绝」逻辑不动。

### D6. 免费转盘机会：新表 `luckywheel_free_spins` + 手数计数列

- 表：`(id, tg_id, source='blackjack', granted_at, expires_at, used_at NULL)`。周配额由 `COUNT(granted_at ≥ 本周一)` 推导，**不存周计数器**——避免周界重置逻辑与漂移。手数进度存 `statistics.blackjack_hands_since_freespin` 列，结算核心同事务累加（D2 同一挂钩点）：每结算一手 +1；`while 进度 ≥ 阈值 and 本周配额有余: 发放机会行, 进度 −= 阈值`（while 而非 if：兼容管理员事后调低阈值的存量进度）。
- 转盘端：`POST /api/luckywheel/spin` 先查可用机会（未用、未过期）→ 有则标记 `used_at` 并以 `cost_override=0` 调 `execute_single_spin`；跳过 `min_credits_required` 校验；负奖品截断、邀请码、`gen_privileged_code` 语义原样复用（奖池读取同一线上配置，不含对免费机会的特判）。十连抽不查免费机会。**不设使用余额上限**（±100 后无放大源；截断区的有界让利已在 D1 论证）。
- **通知**：免费机会发放的 Telegram 通知用**游标轮询任务**（每分钟，镜像奖池播报 `JACKPOT_NOTIFY_CURSOR` 的既有模式）而非路由层挂钩——实现时确认发放散落在全部结算路径（含超时清理等不经路由的路径），只有轮询能全覆盖；游标带 60 秒安全窗避免越过未提交事务。到期提醒为每日任务（查 expires_at 在次日内的未用机会，按用户合并为一条发送）。两者均不在结算事务内做网络调用，发送失败仅记日志。发送量有界：获得通知 ≤ 周上限 5 条 + 每日至多 1 条提醒。发放行**不删除**——保留作台账（对账脚本按周核算让利率依赖它），「过期作废」由可用性查询的过滤实现。
- `wheel_stats` 加 `source` 列（`'paid'` / `'blackjack_free'`，默认 `'paid'`），`cost_credits=0` 仅作辅助标识（避免管理员将参与费调 0 后不可区分）。
- 过期清理：每日调度任务删除/标记 `expires_at < now` 且未用的行；界面可用次数实时按「未用且未过期」过滤，清理延迟不影响不可用性。
- 备选「投注流水计数」被否：见 D1 对比。备选「专用非负小转盘」被否：用户选择普通大转盘的奖品诱人度。

### D7. 配置沿用 blackjack 现有 system_config 配置对象

新增键：`relief_enabled` / `relief_threshold` / `relief_multiplier`、`cashback_enabled` / `cashback_rate` / `cashback_min_payout`、`freespins_enabled` / `freespins_hand_threshold` / `freespins_weekly_cap` / `freespins_expiry_days`。开关关闭即停发新让利，存量（未用免费机会、已入钱包的余额）保留不受影响。阈值调整仅影响其后判定，存量计数与进度保留（spec 已约定）。

## Risks / Trade-offs

- **[三项叠加后 15 分注玩家有效期望 ≈ −0.5%，截断区趋近 0]** → D1 预算表为管理端调整提供核算口径；手数阈值下限 20 写入护栏；若实际数据显示趋近零，优先调高 `freespins_hand_threshold` 或调低 `freespins_weekly_cap`。
- **[线上奖池改回翻倍/减半类奖品，放大效应回归]** → 这是本设计的硬前提。护栏：D1 参数护栏中显式警示；对账脚本（任务 7.1）按周以实际奖池配置重算转盘 EV，放大类奖品一旦出现立即在周报中体现。
- **[低注玩家轻度净补贴（周封顶 +4~9 分）]** → 有界且被观看收入理性支配；该人群是留存目标本身。若管理端不认可，切换投注流水口径（D1 备选）即可闭合，表结构与端点逻辑不受影响，仅计数列语义与配置键变化。
- **[余额 0 玩家免费转盘 EV ≈ +11.5，观感上像白嫖]** → 获取前提是先以 ≥30 余额打满手数，无法主动刷；破产玩家存量未用机会的期望回流约 5×11.5 = 57.5 分（一次性，且其破产过程本身已向系统注入远大于此的抽耗）；7 天有效期自然收敛；这恰是「跌破门槛后回来」的回流钩子。
- **[争霸赛余额锁定引发「取不出来」投诉]** → 规则说明与到账通知均写明来源与「仅可用于报名」；余额不过期。
- **[周结算任务与在线结算竞态]** → 聚合窗口是已闭合的上一完整周期（按 `settled_at`），与进行中手牌无重叠；重跑幂等（D4）。
- **[连败计数 / 手数进度与手牌历史漂移]** → `relief_credits` 与 `payout_credits` 均落 `blackjack_hand` 行，可离线对账；实现任务中含对账脚本。
- **[管理员将转盘参与费调为 0 后免费记录不可区分]** → `wheel_stats.source` 列独立于 `cost_credits` 标识。

## Migration Plan

Alembic 单次迁移，全部新列带默认值、新表空建，零停机：

1. `statistics` 加 `tournament_wallet_credits`（默认 0）、连败计数列、`blackjack_hands_since_freespin`（默认 0）。
2. `blackjack_hand` 加 `relief_credits`（默认 0）。
3. 锦标赛报名表加 `wallet_paid_credits` / `credits_paid_credits`（默认 0）。
4. 新表 `blackjack_weekly_cashback`、`luckywheel_free_spins`（含 `(tg_id, used_at)` 查询索引）。
5. `wheel_stats` 加 `source`（nullable，默认 `'paid'`）。

上线顺序：迁移 → 后端（含调度任务注册）→ 前端。回滚：三项开关全关即回到现状（新列新表留存无害）；迁移不回滚。
