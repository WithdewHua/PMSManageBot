## Context

动机见 `proposal.md` 的 Why。行为契约见本变更的 `specs/blackjack-tournament/spec.md`。本文只记录实现取舍。

当前完赛路径（归档变更 `2026-08-26-add-blackjack-tournament` 决策 9）是：

```
tick 每分钟扫进行中赛事
  → now >= play_deadline_ms
  → force_settle_tournament_hands（每手独立事务）
  → CAS 2→3 → 排名派奖 → 授勋 → 通知
```

闸门只看完赛截止。发牌与动作另有两道门：`status == 进行中`，以及 `now < play_deadline_ms`。原设计明确依赖后者是**与赛事状态无关的固定时间戳**，所以两阶段之间不会冒出新手牌，也就不需要「结算中」中间态。

报名终态（已打完 / 已淘汰）只在手牌结算后写入，手牌热路径**不会**回头推进赛事状态。锁序仍是 `hand → tournament → entry → statistics`。

## Goals / Non-Goals

**Goals:**

- 全员报名终态与完赛截止共用同一条清场 → CAS → 派奖链，不复制一套结算
- 提前完赛不破坏「排名读到终局筹码」：两阶段之间仍不能冒出新手牌或未入账的动作
- 资格门、奖池、勋章、通知去重（CAS）的口径不动
- SQLite 与 PostgreSQL 行为一致

**Non-Goals:**

- 不引入管理员手动完赛
- 不引入「结算中」中间态
- 不把手牌结算与赛事结算放进同一事务
- 不改表结构、不加 `playing_count` 之类的冗余列
- 不改开赛后不可改完赛截止、进行中不可取消
- 不在本变更里修「截止路径上发牌事务与结算 CAS 交错」的预存竞态；那条洞在提前完赛之前就存在，由 `serialize-tournament-deal-and-settle` 处理

## Decisions

### 1. 提前完赛挂在 tick 上，不挂在最后一手的热路径

最后一名打完或被淘汰时，手牌结算已经持有 `hand`，并要写 `entry`。若在这里接着 CAS 赛事、锁全场报名、逐个派奖、授勋，等于把一条跨全场的慢路径塞进每一次赛内结算——而其中只有「恰巧是全场最后一手」才用得到。

tick 已是完赛截止的唯一执行点，一分钟延迟在原设计里就被当成无人可感。全员终态只是给同一个阶段多一个触发条件。

**替代方案**：最后一手结算成功后，若本场已无 `ENTRY_PLAYING`，由该 HTTP 请求走 `BackgroundTasks` 触发结算。否决——通知与派奖会绑在「最后一个打完的人」的请求上，失败重试、超时、与 tick 并发抢 CAS 都要另写一套，而 CAS 本身已经保证只有一方能派奖。不值得。

### 2. 阶段三闸门改为「截止已到 **或** 已无进行中报名」

```
for t in 进行中:
    if now < play_deadline 且 仍有 ENTRY_PLAYING:
        continue
    清场 → CAS 2→3 → 派奖
```

截止路径完全保持现状，含「未打满且未淘汰者失去资格」。全员终态路径上清场几乎总是空转：报名终态是手牌结算**之后**才写的，按不变量此时不应再有非终态手牌。清场仍先跑，因为「带着未终结手牌排名」是不可恢复的。

**替代方案**：只在截止未到时查报名终态，截止已到则跳过查询。否决——省掉的是一次按 `tournament_id` 的 EXISTS，换来两条分叉，而截止路径也要进同一段清场代码。

### 3. 用一次批量查询判断「谁还有进行中报名」，不给赛事表加计数列

tick 已经一次列出进行中赛事。对本轮 id 列表做：

```
SELECT DISTINCT tournament_id
FROM blackjack_tournament_entry
WHERE tournament_id IN (...)
  AND status = ENTRY_PLAYING
```

得到「仍未打完」的集合，阶段三按集合判断即可。N 场进行中赛事每分钟一次 IN 查询，量级远小于手牌热路径。

**不**在 `blackjack_tournament` 上维护 `playing_count`：每次手牌结算都要改赛事行，锁序会从「结算只锁 hand → entry」变成「hand → tournament → entry」，并与报名/派奖抢同一行。为每分钟一次的 tick 付这个成本不划算。

**替代方案**：对每场赛事单独 `EXISTS`。功能等价，N 次往返只是更吵。批量一次即可。

### 4. 两阶段之间「不能冒出新手牌」的不变量，从「截止是固定时间戳」换成「没有人还能发牌」

原决策 9 写过：发牌端点以 `now < play_deadline_ms` 为闸门，故清场与排名之间不可能有新手牌，无需「结算中」。提前完赛发生在截止之前，这句不再成立。

替换不变量：

| 路径 | 谁挡住新手牌 / 动作 |
|---|---|
| 完赛截止已到、尚未 CAS | 发牌与 `_lock_tournament_hand` 上现有的 `now >= play_deadline_ms` |
| 全员终态、尚未 CAS | 发牌已拒绝 `ENTRY_FINISHED` / `ENTRY_ELIMINATED`；终态写在手牌结算之后，此时不应再有在局手牌，动作端点无牌可动 |
| 任一路径 CAS 完成 | `status != 进行中`（发牌与动作都已有这道门） |

因此**不**引入「结算中」。动作端点不必再加「是否还有进行中报名」——那是发牌已经检查过的报名状态，且全员终态时没有在局手牌可操作。

需要改的是注释与心智模型，不是再加一道与截止对称的时间闸门。`status != 进行中` 必须继续作为动作/发牌的第一道门，不能只信截止时点——这正是 delta spec 对「完赛截止与在局手牌的交界」的要求，代码里这道门已经在截止判断之前。

若将来有人把截止判断提到状态判断之前，提前完赛后的动作会在 `status` 已是已结算时仍按「未到截止」放行。实现时保持现有顺序：先状态，后截止。

### 5. 完赛提醒与停用开关不改控制流

提醒阶段仍只在 `now < play_deadline` 的窗口内、向 `ENTRY_PLAYING` 发送。全员终态后 pending 为空，`reminder_sent_at` 照常推进（或根本进不了窗口，因为阶段三已把赛事结掉）。不会对已打完的人补发「你还没打完」。

21 点停用时，进行中赛事本来就不作废；tick 的完赛阶段不看停用开关。提前完赛只是完赛条件多一条，不停用开关分叉。

### 6. 文案只改「把截止说成唯一完赛信号」的那几处

大厅继续展示完赛截止——它仍是未全员终态时的上限，也是开赛私聊、完赛提醒的内容。需要改的是把打满之后写成「等待赛事在完赛截止后结算」的用户提示，改为「等待赛事结算」。

管理端不增加「立即完赛」按钮。

### 7. 开着的牌桌靠排名接口的 `status` 切到已结算，报名终态后轮询

提前完赛把「打完 → 已结算」从几小时缩到大约一分钟。排名接口本来就返回 `status`，但前端只写了 `standings`，刷新也切不走「进行中 / 实时排名」。

`loadStandings` 把返回的 `status` 写回 `this.tournament.status`。报名已终态且赛事仍为进行中、对话框停在牌桌视图时，每 15 秒静默拉一次排名（tick 是一分钟一轮，15 秒足够在下一轮之后看到赛果，又不在进行中牌桌上空转）。切到已结算、回大厅、关对话框时停表。

不另开 WebSocket，不拉赛事详情：排名接口已经带状态和最终名次，一次请求够用。

最后一手还在展示时，`tournament.status` 变成 3 也不得拆掉牌桌——与「决定性一手的结果可见」同一条不变量，条件改为「进行中且报名进行中，或仍有 `hand`」。

### 8. 本变更不把「发牌与结算共享赛事级锁」当成已成立的不变量

发牌只在事务前段读一次 `RUNNING` / 截止，之后锁报名、扣筹码、插手牌，提交前不重检——这是提前完赛落地时的现状。PostgreSQL 上行锁挡不住这条交错。提前完赛路径更难踩（发牌中的报名仍是 `ENTRY_PLAYING`），截止路径的洞由独立变更 `serialize-tournament-deal-and-settle` 用赛事级条件 UPDATE 补上。

本变更继续让 tick 先清场再 CAS，注释不再声称「固定时间戳保证两阶段之间没有新手牌」。

## Risks / Trade-offs

- **[Risk] 最后一手尚未提交、tick 误判全员终态** → 报名终态只在手牌结算事务提交后写入；在局手牌对应的报名仍是 `ENTRY_PLAYING`，批量查询会把它留在「未完赛」集合里。不会在有人还握着牌时派奖。
- **[Risk] 清场与 CAS 之间插入新手牌** → 全员终态路径上所有报名都已是终态，发牌会拒。截止路径上的交错由独立变更 `serialize-tournament-deal-and-settle` 用赛事级条件 UPDATE 串行化发牌与结算。
- **[Risk] tick 列表上限导致最老的进行中赛事迟迟不提前完赛** → 原实现已有：达到 `_TICK_LIST_LIMIT` 记 error。本变更不放宽也不收紧这条；提前完赛与截止完赛走同一份列表。
- **[Trade-off] 最多约一分钟的完赛延迟** → 换来手牌热路径零膨胀、与截止路径同构。原设计已接受该延迟。
- **[Trade-off] 每分钟多一次按进行中赛事 id 的 IN 查询** → 避免冗余列与热路径抢锁。进行中赛事数量按运营预期是个位数到几十，不是热路径。

## Migration Plan

- 无 schema 变更，无数据迁移。部署即生效：下一轮 tick 会把已经全员终态、仍卡在进行中的赛事结掉。
- 回滚：恢复「只看 `play_deadline`」的闸门。已经提前结算的赛事保持已结算——那是合法终态，回滚不得重开。
- 不需要重启恢复函数：周期 tick 仍是唯一推进器。
